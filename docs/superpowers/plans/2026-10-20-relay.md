# Relay Implementation Plan (plan 1 of 2)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A homelab relay that gives the Cardputer one small, stable wss protocol to T3 Code. The relay handles home, threads, replies, launches, questions, approvals, and voice, plus a self-repairing approvals adapter. All of it is testable end-to-end with a terminal device simulator before any firmware exists.

**Architecture:**
- **T3 access:** the relay is a Node/TS service. It talks to T3 over MCP on `127.0.0.1:3773/mcp` for everything except approvals. Approvals go through an isolated adapter speaking T3's internal WS protocol.
- **Device protocol:** it shapes everything into screen-sized view models over one authenticated wss endpoint.
- **Self-repair:** a canary detects adapter breakage on T3 updates, and a repair loop launches a T3 thread to fix it, auto-merging under guardrails.
- **Plan 2** (firmware) consumes `docs/protocol.md`, which this plan produces.

**Tech Stack:**
- Node 22 (installed: v22.23.1), TypeScript, pnpm (installed), vitest
- `ws`, `zod`, `@modelcontextprotocol/sdk`
- `whisper.cpp` (`whisper-server`)
- systemd user service, Tailscale Funnel, GitHub Actions, `gh`

**Spec:** `docs/superpowers/specs/2026-10-20-t3-cardputer-design.md`

## Global Constraints

- **Nothing about the homelab gets committed:** no hostname, tailnet name, IP, token, or relay URL, including in receipts and fixtures. Before every commit, run `grep -rnE '[a-z0-9]\.ts\.net|100\.(6[4-9]|[7-9][0-9]|1[01][0-9]|12[0-7])\.[0-9]+\.[0-9]+|prod-[0-9a-f]+\.t3coderelay' --exclude-dir=node_modules --exclude-dir=.git .`. It must return nothing. Placeholders like `<homelab>.<tailnet>.ts.net` don't match.
- **Every numeric limit** (buffer, budget, timeout, interval, lockout, attempt count) is a named config value with a receipt. The receipt is a one-line `why` comment citing the measurement or `docs/receipts/<file>.md`. A limit hit at runtime produces an error naming the budget, the limit, and the ask, e.g. `reply truncated: max_reply_pages=40, reply needed 57`.
- **The device never receives T3 credentials.** T3 tokens live only in the relay secrets file (`0600`).
- **All T3 internal-protocol code** lives in `relay/src/approvals/`. Nothing outside that folder imports from it except through `relay/src/approvals/index.ts`.
- **Device-bound text is printable ASCII only** (0x20–0x7E plus `\n`). The device font has nothing else.
- **Code style:**
  - No code comments except receipts and external-constraint "why" lines (user policy).
  - Commit messages are lowercase conventional commits with scope `relay`, `docs`, or `ci`, and no agent credit.
- **Relay config** lives in `~/.config/t3-cardputer/relay.json`, secrets in `~/.config/t3-cardputer/secrets.json`, and state in `~/.local/state/t3-cardputer/`. The repo ships only `relay/relay.example.json`.
- **Outward-facing steps need João's go-ahead at execution time:**
  - enabling Tailscale Funnel
  - creating the GitHub fine-grained token
  - registering the project in T3
  - installing system packages

## Review Focus

1. **T3 restarts or updates mid-session.** MCP or WS calls fail, then recover. The device must see `T3 unreachable, retrying` on Home within one poll cycle, then recover on its own, never freeze. Pinned in Task 9 (`session survives T3 outage`).
2. **Reply text the device font can't draw:** emoji, smart quotes, CJK, tabs, ANSI codes, 2,000-char single-line URLs. It must come out as readable ASCII, wrapped, with nothing dropped silently. Pinned in Task 4.
3. **Same device reconnects while its old socket is half-open,** for example on a WiFi to hotspot handoff. The newest connection wins, the old one is closed, and there are no duplicate pushes. Pinned in Task 9.
4. **Device retries a `reply` or `launch` after a reconnect.** It must not double-send to T3. Device message `id` maps to T3 `clientRequestId`. Pinned in Task 9.
5. **Audio stream cut mid-recording (WiFi drop).** The relay discards the buffer after the idle timeout and runs no whisper job. The next session gets no stale transcript. Pinned in Task 11.

### Task 9: Server, sessions, watcher

**Files:**
- Create: `relay/src/server.ts`, `relay/src/session.ts`, `relay/src/watcher.ts`
- Test: `relay/test/session.test.ts` (real `ws` server on an ephemeral port, fake `T3Mcp` and fake `ApprovalsAdapter`)

**Interfaces:**
- Consumes: everything from Tasks 3–8.
- Produces: `relay/src/stt/types.ts` with `interface Stt { transcribe(wav: Buffer): Promise<string> }`. Task 11 implements it; this task's tests use a fake.
- Produces: `startServer(deps: { config: RelayConfig; t3: T3Mcp; approvals: ApprovalsAdapter; auth: DeviceAuth; lockout: Lockout; defaults: DefaultsStore; stt: Stt; approvalsState: () => {available, reason?} }): Promise<{ port: number; close(): Promise<void> }>`
  - HTTP `POST /v1/pair {code, name}` returns `{token}`.
  - WS `/v1/device`: the first frame must be `hello` within a timeout (receipt pending Task 13), or the socket closes with 4401. A bad token records a lockout failure and closes with 4401.
- Produces: `class Watcher(t3, approvals, intervalMs)` with `onChange(cb: (snapshot) => void)`. It polls `listThreads` for every project plus `listPending` for waiting threads. `intervalMs` comes from the Task 1 receipt (e): the smallest interval whose per-poll cost stays under 5% of one core, measured, with the number recorded.
- **Session rules:**
  - On `hello`, send `welcome` then a full `home`. Push a new full `home` only when it differs from the last one sent; it's screen-sized, so no diff protocol.
  - A second session for the same `deviceId` closes the older one with 4000.
  - `reply`/`launch` use `clientRequestId = deviceId + ":" + id`. A repeated `id` gets the cached `ack` without calling T3 again.

### Task 14: Self-repair loop and auto-merge guardrails

**Interfaces:**
- Produces: `checkMergeable(pr: { headRepo: string; baseRepo: string; headRef: string; files: string[]; checks: { name: string; conclusion: string }[] }, expected: { repo: string; branch: string }): { ok: true } | { ok: false; reasons: string[] }`
  - Requires:

- Produces: `class RepairOrchestrator` with `onBroken(reason, versions: {from, to})`:

  - Launches via `T3Mcp.launch` on the `t3-cardputer` project, with `workspace: "worktree"`, branch `repair/t3-<to>-<attempt>`, and `runtimeMode: "full-access"` (or the level from Task 1 receipt (d)). **Spec coverage:**
- Goals 1–5 map to Tasks 7, 9, 6, and 11.

- Launcher and firmware are in plan 2.
- Anti-goals:
  - no T3 creds on the device: Global Constraints + Task 8

  - unmeasured limits: receipts throughout
  - leak: grep in CI

**Deviation from spec, on purpose:** the spec says the relay "pushes diffs". This plan pushes the full `home` view on change instead, because it's screen-sized (`maxHomeRows` rows). A diff protocol would be solving a problem we don't have.
